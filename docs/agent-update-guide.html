Overview

Zero-touch updates for the shop PC

Previously, updating the print agent on the shop PC required re-shipping a zip file and walking a non-technical client through reinstalling it. Every code change — bug fix, new printer feature, dependency update — was stuck behind that manual process.

This feature makes updates invisible to the client. The developer publishes a release from their machine, presses Install in the admin dashboard topbar, and the agent on the shop PC downloads, verifies, swaps, and restarts itself — rolling back automatically if anything goes wrong. The client never touches anything.

Key invariant: Every failure branch ends with the old version printing. Worst case is the shop stays on its current version — exactly where it is today.
What Was Built

New files and what each one does

FilePurpose
agent/version.json Single source of truth for the running agent version. Bundled in every zip. Checked after a swap to verify extraction was complete.
agent/src/update-lib.ts Pure helpers: compareVersions(a,b), parseLatestJson(raw) (validates Storage manifest), sha256Hex(buf). No side effects — fully unit-tested.
agent/src/updater.ts Full update pipeline. Polls agent_config for a command, downloads + verifies zip, extracts to staging, writes the bat, exits agent. Also handles post-update status reporting and the 30s periodic heartbeat.
agent/updater-template.bat Windows batch script that swaps files. Runs as a separate SelfPrintUpdater scheduled task (outside the agent's process). Renames engine dirs → restarts agent → polls for heartbeat → deletes backup on success, or restores on timeout.
scripts/package-for-shop.mjs Extended with --publish flag. Detects code-only (~100 KB) vs full (~100 MB) payload, sha256s the zip, uploads it to agent-updates bucket, writes latest.json last, then deletes old zips.
scripts/push-agent-update.mjs CLI trigger — writes the same agent_config row as the dashboard Install button. Use from terminal or CI.
src/app/api/admin/agent-update/route.ts GET returns agent state + latest published version. POST triggers install (super_admin only). Treats in-flight status older than 30 min as stale so the button re-enables after a stuck update.
src/components/admin/AgentUpdateBadge.tsx Topbar navbar badge (super_admin only). Expanding-ring dot animation when update available. Popup with running version, available version, and Install button. Page-open banner once per session. SWR polls 5s in-flight, 60s at rest.
supabase/migrations/20260806000000_agent_self_update.sql Adds 6 columns to agent_config and creates the agent_update_events audit table. Must be applied to Supabase before the feature works.
Architecture

How an update flows end to end

Key point: The admin dashboard never touches the shop PC directly. It writes one DB row. The agent — already running on the shop PC — pulls everything itself over outbound HTTPS. No open ports, no VPN, no SSH.
Developer bumps version + publishes
Edit agent/version.json → run npm run package:shop -- --publish. Zip lands in private agent-updates Supabase bucket. latest.json written last.
Admin clicks Install in topbar navbar
POST /api/admin/agent-update writes update_target_version and update_status = requested to agent_config table in Supabase.
Agent picks up command (~1s via Realtime, max 30s poll)
Agent has a persistent WebSocket to Supabase Realtime. DB row change pushes instantly. 30s fallback poll covers Realtime drops. Waits if a print job is in progress.
Download → verify SHA-256 → extract
Downloads zip from agent-updates bucket via service-role key. Verifies sha256 against latest.json. Extracts to update-staging/.
Writes BAT + exits
Generates run-update.bat with paths baked in. Writes update-pending.txt. Sets status swapping. Calls process.exit(0) — Windows Scheduled Task auto-restarts it.
New boot → hands off to SelfPrintUpdater task
Restarted agent sees update-pending.txt, launches SelfPrintUpdater scheduled task (sibling process — not a child), exits again so the BAT can touch its files.
BAT swaps files on disk
Renames engine → engine.bak (5-attempt retry). For code update: copies new agent/ only. For full update: renames extracted dir to engine. Starts SelfPrintAgent task.
New agent boots + runs self-check
PDFium WASM loads, Sharp native binding works, ≥1 printer enumerable, Supabase reachable. All pass → writes agent-health.txt, sets DB to completed.
BAT sees heartbeat → success
Deletes engine.bak and staging files. Writes agent_update_events audit row.
No heartbeat within 3 min → automatic rollback
BAT renames engine.bak → engine, starts old SelfPrintAgent. Old agent sets status rolled_back with reason. Client keeps printing — zero interruption.

Developer Workflow

Publishing an update (every release)

Step 1 — Bump the version

Edit agent/version.json:

{ "version": "1.0.1" }

Must be dotted numeric and strictly greater than the currently published version. The publish script checks and refuses to proceed if not. Cannot republish an existing version.

Step 2 — Run the publish command

npm run package:shop -- --publish

What this does automatically:

  1. Validates agent/config.json has real credentials
  2. Resolves pinned versions of the 4 agent deps from package-lock.json
  3. Decides payload kind: code (~100 KB) if only scripts changed, full (~100 MB with node_modules) if a dep version moved
  4. Strips config.json from payload — shop credentials never travel in a zip
  5. Checks bucket: refuses if this version already exists
  6. Uploads agent-1.0.1.zip to bucket
  7. Writes latest.json last (zip first so manifest never points at missing file)
  8. Deletes all previous agent-*.zip files (only current version kept)
First publish? Always produces a full zip (no previous manifest to compare deps against). Subsequent releases are usually code-only unless you update a runtime dependency.

Step 3 — Trigger the install

Option A — Admin dashboard (recommended):
Log in as super_admin. The Update button appears in the topbar navbar when the agent's running version differs from the published version. Click it → popup opens → click Install v1.0.1.

Option B — Terminal:

npm run agent:push-update

Both write the same agent_config row. Agent picks it up via Realtime within ~1 second.

Step 4 — Watch progress in the topbar badge

The badge polls every 5 seconds while in-flight and updates in real time:

StatusMeaning
requestedDB row written, agent hasn't polled yet (max ~30s)
downloadingAgent downloading zip from Supabase Storage
swappingAgent exited, BAT is renaming files on disk
completedNew version running and healthy — badge disappears
failedAborted before swap — old version still running, safe to retry
rolled_backSwap ran, new version failed health check, old version restored
Mid-print job? The agent defers the update until the job finishes. Max ~5 minutes of extra wait.
Under the Hood

What happens on the shop PC in detail

Why a separate BAT task?

Windows prevents a process from replacing its own executable while it's running. The agent can't overwrite engine/ from inside it. Solution: the agent exits → Windows restarts it → the new boot immediately launches SelfPrintUpdater as a sibling scheduled task (not a child process), then exits again. The BAT runs freely outside any agent process and renames the dirs.

File layout during a swap

Before swap:                   After successful swap:
<shop-root>/                   <shop-root>/
├── engine/      (old)          ├── engine/          (new version)
├── update-staging/             ├── engine.bak/      (deleted after heartbeat)
│   └── update-extract/ (new)  └── update-staging/  (cleaned up)
└── update-pending.txt

Heartbeat files

FileWritten byConsumed by
agent-health.txtAgent every 30sBAT waits for it post-swap
update-pending.txtAgent pre-exitNext boot → triggers updater launch
update-rollback.txtBAT on rollbackAgent reads on boot → sets DB status
update-failed.txtBAT on timeoutAgent reads on boot → sets DB status

Safety

Rollback and manual recovery

Automatic rollback (normal path)

If the new agent fails its startup self-check (any of: PDFium fails to load, Sharp binding broken, no printers, Supabase unreachable), no heartbeat is written. The BAT waits 3 minutes, then:

  1. Renames engine → engine-broken
  2. Renames engine.bak → engine
  3. Starts SelfPrintAgent → old version boots
  4. Old agent sets DB status rolled_back with reason string

Dashboard badge turns red. Shop keeps printing. Fix the build and re-publish.

Manual recovery (rare — power loss mid-swap)

If power was lost exactly during the file rename, engine.bak may exist but engine is gone. On the shop PC in PowerShell:

# In the directory where you extracted the zip (e.g. C:\SelfPrint):
Rename-Item engine.bak engine
schtasks /Run /TN SelfPrintAgent

If both engine and engine.bak exist and you want to revert:

Remove-Item engine -Recurse -Force
Rename-Item engine.bak engine
schtasks /Run /TN SelfPrintAgent
Troubleshooting

Common problems and fixes

Dashboard shows "Updating…" forever

Status stuck at requested or downloading. Agent not picking up the command.

  1. Check Windows Task Scheduler on shop PC for "SelfPrintAgent" — must be Running
  2. If missing: run SETUP.bat again on shop PC
  3. Check shop PC internet connection
  4. Reset stuck status manually in Supabase SQL Editor:
UPDATE agent_config
SET update_status = null, update_target_version = null,
    update_started_at = null, update_message = null
WHERE id = 1;

Then retry from the dashboard.

Status shows failed

Agent aborted before handing off to BAT. Old version still running. Check engine\agent\agent.log on shop PC.

Log saysFix
SHA-256 mismatchCorrupted download — retry; if persistent, re-publish
latest.json missingRe-create agent-updates bucket or re-publish
SelfPrintUpdater not foundRun SETUP.bat again on shop PC
Downgrade refusedBump agent/version.json higher before re-publishing

Status shows rolled_back

Swap ran but new version failed health check. Old version restored. Check in order:

  1. update-staging\updater.log on shop PC — BAT's own trace
  2. engine\agent\agent.log — look for "SELF-CHECK FAILED"
  3. If updater.log says "ROLLBACK FAILED": rename engine.bak → engine manually

Internet drops mid-update

When it dropsEffect
Before download startsAgent retries on next 30s poll — no harm
Mid-downloadDownload fails → failed → retry from dashboard
After download (zip on disk)Swap runs offline (file renames) — completes fine
After swap, before heartbeatNo heartbeat → BAT rolls back after 3 min
After heartbeat writtenDone — DB updated when connection recovers
